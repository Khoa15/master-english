# data/source

Source files for `tools/build_vocabulary.py`, which builds `app/src/main/assets/data/vocabulary.json`.

## pack/2 — the standard for curated packs

`tet.json`, `christmas.json`, `all1000.json` and `oxford.json` use it. A file is one pack (or, for `oxford.json`, several); every language is a key, never a column.

```json
{
  "format": "masterenglish.pack/2",
  "pack": {
    "id": "TET",
    "title": {"en": "Tet Holiday", "vi": "Tết"},
    "cefr_level": "TET",
    "source": {"name": "...", "url": null, "dictionary": null, "note": "..."}
  },
  "entries": [
    {
      "id": "tet_chung_cake",
      "term": "Chung cake",
      "lang": "en",
      "rank": 12,
      "pronunciation": {"us": "/tʃʊŋ keɪk/"},
      "also_called": ["..."],
      "source_url": "...",
      "senses": [
        {
          "pos": "noun",
          "definition": {"en": "Square sticky rice cake ..."},
          "translations": {"vi": "bánh Chưng"},
          "examples": [
            {"text": "Every year, my grandmother and I wrap Chung cake together.",
             "translations": {"vi": "Hằng năm, tôi và bà cùng gói bánh Chưng."}}
          ],
          "tags": ["food"]
        }
      ]
    }
  ]
}
```

Rules (checked by `add_pack` in the build script):

- `id` is written in the file and never changes. Learner progress is keyed by it. Convention: `<pack prefix>_<slug of term>`.
- Language keys are BCP-47 codes (`vi`, `ja`, `fr`, `pt-BR`). A missing translation is a missing key, not `null` or `""`; the app falls back to `en`.
- `definition` is a map too, so a definition in another language can be added later. `translations` is the short meaning shown on the card.
- `examples` is a list (any number, each with its own translations). The first one is the one the app shows today.
- `term` should appear in each example's `text`.

To convert an old-shape file (flat `vietnamese`, `example`, `example_vi`): `tools/convert_pack_v2.py`.

`all1000.json` is pack/2 too, with no translations or examples yet. Its entry ids are the ids the build used to generate (an entry whose id is already a word from the Oxford lists is only linked into the COMMON pack; the word keeps its Oxford content). The build keeps the first 2 definitions per part of speech and at most 6 senses for the words it adds from this file.

`oxford.json` is pack/2 in its multi-pack form: a top-level `packs` list (A1…C1) instead of `pack`, and each entry lists its pack ids in `packs` (the 16 B2/C1 headwords are in two). Its `sources` list carries the metadata and attribution of the dumps it came from (dictionaryapi.dev entries are CC BY-SA 3.0, partly from Wiktionary). Per entry it also keeps `source`, `list_pos` (the part of speech of the Oxford list) and `needs_review`. It is generated by `tools/convert_oxford_v2.py` from `raw/` (the original crawler dumps and `definition_overrides.json`, kept for provenance); after the conversion `oxford.json` is the file to edit, `raw/` is not read by the build. The ids in it are the ones the build used to generate, so progress is kept.

## What the build writes

`vocabulary.json` keeps the legacy sense keys (`definition`, `definition_vi`, `example`, `example_vi`) that the app reads today, and adds `translations` and `examples` to senses that have them, plus `titles` on packs. The app reads them: Room schema 5 (`app/schemas/.../5.json`, migration `MIGRATION_4_5`) has `sense_translations`, `sense_examples`, `example_translations` and `pack_titles`, filled by `LocalDataSeeder`. An asset without the new keys still works (`definition_vi` / `example` / `example_vi` are read as the `vi` translation and first example).
